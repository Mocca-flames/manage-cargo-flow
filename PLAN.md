## 0. Rules you must follow

1. **Never invent an endpoint, field, status value or schema.** The API's real shape lives in `src/api/schema.d.ts` (generated). If something you need is not in that file, **stop and ask the human**.
2. **Never edit `src/api/schema.d.ts` by hand.** Regenerate it with `npm run api`.
3. **Plain CSS only.** No Tailwind, no CSS-in-JS, no UI kits (MUI, Chakra, shadcn, Bootstrap). All styles go in `.css` files and inside a `@layer` (see Phase 3).
4. **No extra libraries.** The only runtime dependencies are listed in section 2. No axios, Redux, Zustand, moment, lodash, form libraries. Ask before adding anything.
5. **Keep API field names exactly as the backend writes them (snake_case):** `staff_role`, `full_name`, `must_change_password`. Do not convert to camelCase.
6. **No `any`.** Use generated types. If a type error appears, fix the cause. Do not silence it with `any`, `as any` or `@ts-ignore`.
7. **After every phase run `npm run build` and `npm run lint`.** Both must pass with zero errors before you continue.
8. **Commit after every phase** with a clear message (e.g. `phase 4: api client`).
9. **Server is the real security.** Hiding buttons by role is only cosmetic. Never assume the UI check protects anything.
10. **Do not store anything in `localStorage` except the auth token** (via `src/auth/token.ts`).
11. **Mobile first.** Every screen must be usable at 360px width. Buttons at least 44px tall.
12. When this guide says **STOP AND ASK**, stop and ask the human. Do not guess.
13. **Save every file as UTF-8.** UTF-16 files pass `tsc` but break vite's bundler and oxlint with "stream did not contain valid UTF-8". (PowerShell 5.1's `Out-File` writes UTF-16 by default — write UTF-8 without BOM instead.)

## 1. What we are building

An internal **admin and director portal** for a freight logistics company. It is an installable PWA that is later wrapped as an Android APK. Updates are pushed by deploying a new web build, with no APK rebuild.

Roles (from the backend): `director` > `admin` > `manager` > `technician` > `user`.
Only **admin** and **director** can use this portal.
Only **director** can create or manage admins/directors and change roles.

Screens in scope:

| Screen | Roles |
|---|---|
| Login, Change password | everyone (must_change_password forces it) |
| Companies list and detail (verify, reject) | admin, director |
| Document review (approve/reject, expiry) | admin, director |
| Load interests (list, update, convert) | admin, director |
| Users (create now; list/manage after backend supports it) | admin, director (director-only actions hidden from admin) |

Out of scope: driver app, GPS tracking, push notifications, payments.

## 2. The locked stack

| Concern | Choice |
|---|---|
| Build tool | Vite |
| UI | React + TypeScript |
| Routing | `react-router` (v7, `createBrowserRouter`) |
| Server state | `@tanstack/react-query` via `openapi-react-query` |
| API client | `openapi-fetch` + types generated by `openapi-typescript` from the backend's `/openapi.json` |
| Client state | None. Auth context only. Filters live in the URL (`useSearchParams`). |
| Styling | Plain CSS with `@layer`, native nesting, CSS variables |
| PWA | `vite-plugin-pwa` (`generateSW` mode, update prompt) |
| Hosting | Cloudflare Pages via Wrangler (`.pages.dev` or custom domain), not Netlify |
| APK | Bubblewrap (Trusted Web Activity) |

Why generated types: the backend appears to be FastAPI (Pydantic schemas). FastAPI publishes `/openapi.json`, so the frontend types come from the real API and you write no hand-made API modules.

## 6. Phase 3: CSS foundation

**Rules for all CSS in this project:**

- Every rule lives inside a named `@layer`. Unlayered CSS beats all layered CSS and would break the system.
- Layer order is declared **once**, in `index.css`, and `index.css` is imported **first** in `main.tsx`.
- Use native nesting (`&`) and CSS variables. Never hardcode colours or spacing inside components. Use tokens.
- The brand palette is the canonical source of truth. Keep the color names stable and change values in one place when the brand evolves.
- Global reusable pieces go in `components.css`. Page-specific CSS goes next to its page in `features/<name>/<name>.css`, wrapped in `@layer features { ... }`, and **every class is prefixed with the feature name** (e.g. `.companies-filters`). This prevents collisions.
- BEM-style naming for parts: `.block`, `.block__part`, `.block--variant`.

## 7. Phase 4: API layer

### 7.1 Generate types

1. Start the backend locally.
2. Run `npm run api`. This writes `src/api/schema.d.ts`.
3. **Commit `schema.d.ts`**. CI builds must not need the backend running.
4. List the available paths so you know what exists:


### 7.3 `src/api/errors.ts`

```ts
// Turns any thrown/returned API error into a human-readable message.
// FastAPI errors look like { detail: "text" } or { detail: [{ msg: "text", ... }] }.
export function errorMessage(err: unknown): string {
  if (err && typeof err === "object" && "detail" in err) {
    const detail = (err as { detail: unknown }).detail;
    if (typeof detail === "string") return detail;
    if (Array.isArray(detail)) {
      return detail
        .map((d) => (d && typeof d === "object" && "msg" in d ? String((d as { msg: unknown }).msg) : String(d)))
        .join("; ");
    }
  }
  if (err instanceof TypeError) return "Network problem. Check your connection and try again.";
  if (err instanceof Error) return err.message;
  return "Something went wrong. Please try again.";
}
```

Important: `openapi-react-query` throws the **response body** for errors, not the HTTP status. So rely on the server's `detail` text for messages. Do not write code that depends on the status code of a mutation error.

### 8.5 `src/auth/AuthProvider.tsx`

```tsx
/* eslint-disable react-refresh/only-export-components */
import { createContext, useCallback, useContext, useEffect, useMemo, useState, type ReactNode } from "react";
import { useQueryClient } from "@tanstack/react-query";
import { getToken, setToken } from "./token";
import { fetchCurrentUser, requestToken } from "./authApi";
import { can } from "./permissions";
import type { AuthUser } from "./types";

interface AuthValue {
  user: AuthUser | null;
  ready: boolean; // false until the first "who am I" check finishes
  login: (email: string, password: string) => Promise<void>;
  logout: () => void;
  reload: () => Promise<void>;
}

const Ctx = createContext<AuthValue | null>(null);

export function AuthProvider({ children }: { children: ReactNode }) {
  const queryClient = useQueryClient();
  const [user, setUser] = useState<AuthUser | null>(null);
  const [ready, setReady] = useState(false);

  const logout = useCallback(() => {
    setToken(null);
    setUser(null);
    queryClient.clear();
  }, [queryClient]);

  const reload = useCallback(async () => {
    if (!getToken()) { setUser(null); return; }
    try {
      setUser(await fetchCurrentUser());
    } catch {
      logout();
    }
  }, [logout]);

  useEffect(() => {
    void reload().finally(() => setReady(true));
  }, [reload]);

  useEffect(() => {
    window.addEventListener("auth:expired", logout);
    return () => window.removeEventListener("auth:expired", logout);
  }, [logout]);

  const login = useCallback(async (email: string, password: string) => {
    const token = await requestToken(email, password);
    setToken(token);
    const me = await fetchCurrentUser();
    if (!can.usePortal(me.staff_role)) {
      logout();
      throw new Error("This portal is for admin and director accounts only.");
    }
    setUser(me);
  }, [logout]);

  const value = useMemo(() => ({ user, ready, login, logout, reload }), [user, ready, login, logout, reload]);
  return <Ctx.Provider value={value}>{children}</Ctx.Provider>;
}

export function useAuth(): AuthValue {
  const v = useContext(Ctx);
  if (!v) throw new Error("useAuth must be used inside <AuthProvider>");
  return v;
}
```

## 13. Phase 9: PWA behaviour and updates

### How updates reach users

1. You push to `main`. The host builds and deploys.
2. The service worker (generated by `vite-plugin-pwa`) detects the new build. This is checked on app load and, thanks to `UpdateToast`, **every hour** while the app stays open.
3. The user sees "A new version is available" and taps **Reload**.
4. The footer now shows the new commit hash. Use this to confirm.

### Caching rules

- **Precached:** the app shell (HTML, JS, CSS, icons). The app opens instantly and works as an installed app.
- **Not cached:** all API calls. This avoids stale-data bugs for a system where data changes constantly.
- Optional later: runtime caching for rarely changing data (e.g. document types). Use `workbox.runtimeCaching` with `StaleWhileRevalidate` for `GET /document-types` only. **Never** cache auth endpoints.

### Backwards compatibility rule (important)

Users may keep running the old frontend until they tap Reload. So when the backend changes:

1. Deploy the backend change in a way that **still works with the previous frontend** (add fields and endpoints, do not remove or rename them yet).
2. Deploy the new frontend.
3. Remove the old behaviour in a later release, after users have updated.

### Testing the PWA (do not trust `npm run dev`)

```bash
npm run build
npm run preview
```

Open the preview URL in Chrome. Open DevTools > Application > Manifest and Service Workers, and confirm there are no errors. Run Lighthouse (PWA/installability). Check that the app is installable.

**CHECKPOINT 9:** the production preview is installable and registers a service worker. Commit.

## 15. Phase 11: Android APK (Trusted Web Activity)

A TWA is a thin Android shell that opens your hosted site in Chrome with no browser UI. Web updates reach the app without a new APK. You only rebuild the APK when the Android wrapper itself changes (icon, name, package ID, colours).

### 15.1 Prerequisites

- The site is live on HTTPS and passes the installability check.
- The manifest is reachable at `https://manage.cargoflowafrica.co.za/manifest.webmanifest`.
- Chrome is installed on the test phone.

### 15.2 Build

Do this in a **separate folder** outside the web project (e.g. `freight-twa/`):

```bash
npm i -g @bubblewrap/cli
mkdir freight-twa && cd freight-twa
bubblewrap init --manifest https://manage.cargoflowafrica.co.za/manifest.webmanifest
bubblewrap build
```

- On first run Bubblewrap offers to download a JDK and the Android SDK. Accept.
- Choose the **package ID once** (e.g. `com.yourcompany.freightops`) and **never change it**.
- Bubblewrap creates a **signing keystore**. **Back it up somewhere safe and secure** (password manager or encrypted storage) and **never commit it to git**. If you lose it, installed copies of the app cannot be updated, only uninstalled and reinstalled.
- Commit `twa-manifest.json` only. The Android project files are generated.
- Output: a signed `app-release-signed.apk` (for direct install) and an `.aab` (for Google Play).

### 15.3 Digital Asset Links (the step that most often goes wrong)

Android verifies the app owns the website through `assetlinks.json`. If it is missing or wrong, the app shows a browser address bar or may fail to launch properly.

1. Get the SHA-256 fingerprint of the signing key (Bubblewrap prints it during build, or run `keytool -list -v -keystore android.keystore`).
2. Generate the file: `bubblewrap fingerprint generateAssetLinks`
3. Copy the resulting `assetlinks.json` into the **web project** at `public/.well-known/assetlinks.json`.
4. Deploy the web project.
5. Verify:

```bash
curl -i https://manage.cargoflowafrica.co.za/.well-known/assetlinks.json
```

It must return **200** with JSON (not the SPA's `index.html`). Also check it with Google's Digital Asset Links "Statement List Generator and Tester".

If you later publish through Google Play with Play App Signing, **add the Play signing key's SHA-256 fingerprint too** (both fingerprints can live in the same file).

### 15.4 Install and test

```bash
bubblewrap install    # installs the APK on a connected device (USB debugging on)
```

Or send the APK file to the phone and allow "Install unknown apps". Confirm: full screen with no address bar, login works, an update pushed to the web appears via the Reload banner.

### 15.5 Later changes

- Changing icon/name/colours/package settings: edit `twa-manifest.json`, then `bubblewrap update`, then `bubblewrap build`. This increments the version code.
- If you publish to Google Play: Play has target-API requirements for new apps and updates (for 2026 reports say API level 36). Rebuild with a current Bubblewrap before your next Play update. This does not apply to APKs distributed directly inside the company.
- **If drivers will need background GPS tracking**, a TWA is not suitable (it runs in the browser engine). Tell the human. The alternative is to wrap the same React code with Capacitor.

**CHECKPOINT 11:** the APK installs, opens full screen, and loads the live app.

Authentication: Bearer token. Roles: admin or director. **Director > Admin.** Director can create and manage admins and directors. Admin cannot create or promote to admin/director.

### Users

|---|---|---|---|

## 18. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| TypeScript cannot find `virtual:pwa-register/react` | Missing type entry | Add `"vite-plugin-pwa/react"` to `types` in `tsconfig.app.json` |
| Styles have no effect or the wrong styles win | A rule is outside an `@layer`, or `index.css` is not imported first | Wrap in the right layer; check import order in `main.tsx` |
| Login works in dev, fails in production | CORS not configured, or `VITE_API_URL` not set | Section 14.1; check the host's environment variables |
| Every API call returns 404 in production | Dev `/api` proxy base used in production | Set `VITE_API_URL` to the real API URL and redeploy |
| Refreshing `/companies` gives 404 | SPA fallback missing | Section 14.2 |
| Users never see updates | `sw.js` cached by host or CDN | `_headers` file (section 5.8); confirm with `curl -I` |
| Update banner never appears in dev | Service worker is not active in `npm run dev` | Test with `npm run build && npm run preview` |
| TypeScript error on a path like `"/auth/login"` | The endpoint does not exist under that name | Read the real paths from `schema.d.ts` (section 7.1) |
| Type error on `status` query value | Schema types it as a union | Make `STATUS_OPTIONS` match the union exactly |
| Mutation error handling by HTTP status does not work | `openapi-react-query` throws the response body, not the status | Show `errorMessage(e)` and rely on the server's `detail` |
| APK shows a browser address bar | `assetlinks.json` missing, wrong, or fingerprint mismatch | Section 15.3; verify with `curl -i` that it returns JSON |
| `assetlinks.json` returns the app's HTML | SPA fallback intercepting | Make sure the file is in `public/.well-known/` and deployed |
| Cloudflare rejects `_redirects` ("infinite loop") | Host handles SPA fallback itself | Delete `public/_redirects`, redeploy, test a deep link |
| Logged out immediately after login | A 401 from another call right after login | Check the token field name used in `requestToken` and the Authorization header |
| `login` succeeds but a non-admin role gets in | `can.usePortal` not applied | Confirm the check in `AuthProvider.login` |
| Build or oxlint fails with "stream did not contain valid UTF-8" | File was saved as UTF-16 (PowerShell 5.1 `Out-File` default) | Re-save the file as UTF-8 without BOM; see rule 13 |
